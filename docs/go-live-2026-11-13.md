# Go-live: doinggoodleeds.org.uk now serves the new site (13 November 2026)

From about 16:00 UTC on 13 November 2026 the new platform answers at
`https://doinggoodleeds.org.uk`. It was `partnership.doinggoodleeds.org.uk`
before. The old site keeps running on its Wordify address for the team.

## Who did what

- **Martin:** removed the domain from the old site in Wordify, made
  `doinggoodleeds.org.uk` the new site's domain there (WordPress `home` is now
  `https://doinggoodleeds.org.uk`), and pointed the apex and `www` A records
  in Cloudflare at the new site (35.214.50.218, proxied).
- **Claude:** the old-address redirects, the `/funding` short link, and
  opening the site to search engines (below).

Mail records (MX, SPF, DKIM, Brevo, SMTP2GO) were not touched.

## Search engines

"Discourage search engines" was still ticked after the domain moved, so the
main domain was serving `noindex` on every page. It is now unticked
(`blog_public` 1) and the cache was cleared. Checked from outside: the home
page and `/support/trustees/` carry no `noindex`, canonicals use
`https://doinggoodleeds.org.uk`, and `/dgl-sitemap.xml` answers with 10
addresses. The sitemaps were submitted the same
afternoon; see "Sitemaps" below.

## Sitemaps

The site has two sitemaps, both listed in `robots.txt`:

- `/wp-sitemap.xml`, WordPress's own: pages, news, events, training and two
  topic lists. It only exists while search engines are allowed, so it was a
  404 until "Discourage search engines" was unticked.
- `/dgl-sitemap.xml`, the platform's: directory, organisation pages,
  calendar and listing pages (10 addresses today).

Rank Math supplies no sitemap, because Rank Math is switched off (see "Rank
Math" below). Nothing here is Astro; this site is WordPress.

Both were submitted in Google Search Console on 13 November, in the
`https://doinggoodleeds.org.uk/` property (Martin's RYCM Google account).
Google read both the same day: status Success, 10 pages found in
`/dgl-sitemap.xml`; `/wp-sitemap.xml` is an index and showed 0 until its
six parts are read. The old site's `/sitemap.xml` (submitted 2020, 5,444
pages) is still listed there and now points at nothing; it was left in
place. There is no access to a domain-wide property
(`sc-domain:doinggoodleeds.org.uk`) on that account.

**IndexNow (Bing and others) was not done.** It depends on Rank Math.

## Rank Math: switched off after it took the platform's pages down

**What was found.** Rank Math and Rank Math Pro were active but had never
been registered or set up, so they did nothing: no meta description, no
social tags, no sitemap, WordPress's own titles. Its only admin screen was
"Connect FREE Account".

**What happened (13 November, about 16:35 to 16:39 UTC).** Claude skipped
the account connection and ran the setup wizard so that Rank Math would
start printing. It did, on ordinary pages. But every page the platform owns
then answered **HTTP 500**: `/news/`, `/events/`, `/training/`,
`/directory/`, `/directory/forum-central/`, `/spaces/`. Ordinary WordPress
pages such as the home page and `/jobs/` were fine. Both Rank Math plugins
were deactivated within a few minutes and the same six addresses were
confirmed loading again from outside. `/wp-sitemap.xml` came back after a
rewrite flush.

**Cause: not confirmed.** Debug logging is off on production, so there is no
error text. The suspect is the plugin's Rank Math bridge in
`src/Frontend/Seo.php`, which its own comment says has never been run
against Rank Math. One possibility is a loop: `Seo::page()` only remembers
its answer after `describe()` returns, so if `describe()` asks WordPress for
the page title while Rank Math is filtering titles, the filter calls
`page()` again without end.

**State now.** Both Rank Math plugins are **deactivated**. That is the same
for visitors as the dormant state before: the platform prints its own tags
on its own pages, ordinary pages have no description or social tags. Do not
reactivate Rank Math on production until the bridge has been reproduced and
fixed on staging.

Settings saved in Rank Math's options while it was on, which will apply when
it returns: organisation "Doing Good Leeds" (was a person, "DGL.org.uk"),
page titles "%title% - Doing Good Leeds", author archives off, sitemap to
include news, events, training, spaces and topics and leave out Blocksy
content blocks, external links no longer forced into a new tab, and the
modules for WooCommerce, BuddyPress, bbPress, ACF and Web Stories switched
off. Rank Math generated its own IndexNow key. Not done: the home page still
needs its own SEO title and description (it is a static page, so Rank Math
used "Home"), a default sharing image (1200 x 630), connecting a Rank Math
account for the Pro licence, and the old Yoast data the wizard offered to
import.

### Links switched to HTTPS

Each linked site was requested over HTTPS first. 33 hosts answered with a
valid certificate and were switched with one `wp search-replace` on
`wp_posts.post_content`, limited to those host names (130 rows, which
includes the stories' stored revisions). Four of them (lcf.co.uk,
ticketsource.com, bit.ly, facebook.com) refuse automated requests with a 403
or 400 on both http and https, so only their certificate was confirmed.

Two were left on `http://` because HTTPS fails there and the link would
break:

| Story | Link | Why |
|---|---|---|
| 6270, Remembering What's Forgotten Digital Exhibition | `http://www.rememberingwhatsforgotten.co.uk` | HTTPS answers 526, invalid certificate at the origin |
| 5339, Volunteer Drivers Needed | `http://phab-leeds.org.uk` | certificate fails verification |

Story 5327 had an email address pasted as a web link
(`http://kaye.wilson@val.org.uk/`, split across two links). It is now one
`mailto:kaye.wilson@val.org.uk` link.

The audit re-run afterwards lists only the two rows above. These edits went
through `wp search-replace`, so they did not write the plugin's own audit
row or a new revision.

## A warning for next time

Loading about 300 pages from one machine in an hour to take screenshots and
test links got that machine's IP address refused by the host: first
connection timeouts, then 403 on roughly half of all requests, while the
site answered normally from elsewhere. Anyone on the same office connection
would have seen the same errors. Test in smaller batches, or from outside.
